# FORK-PLAN.md: Resolve-class 6.2K HEVC editing on CachyOS + RX 6700 XT

This is the long-term plan for this personal fork of FilmCraft. It spans many sessions.
**At the start of every session, read this file, then the "Progress log" at the bottom, and
continue from the first unfinished step.** Update the progress log as you go.

Goal: for one workflow (cutting, grading and exporting Fujifilm X-M5 6.2K H.265 footage), this
fork should feel comparable to DaVinci Resolve Studio on Windows on the same PC. Time to
implement does not matter. Correctness, stability and measured performance do.

---

## 1. Fork rules (the owner's decisions; these override CLAUDE.md / AGENTS.md where they conflict)

- **FFmpeg may be used as an external process** (the system `ffmpeg`/`ffprobe` binaries), never
  linked and never bundled in any package. It is a fallback and a benchmark oracle, not the
  long-term hot path.
- **In-process OS video APIs are allowed and preferred for the hot path:** VA-API through libva
  (MIT) and Vulkan Video through Mesa RADV, via Rust bindings (e.g. `cros-libva`, `ash`). These are
  license-clean; nothing GPL/LGPL gets linked.
- **Still in force:** never crash (no `unwrap`/`expect`/`panic!` outside tests, `Result`
  everywhere, hostile-input handling), exact `Tick` time, everything is a command, the layering
  rules, and `cargo xtask ci` green before each commit.
- **`unsafe` stays confined** to FFI modules, each with a `// SAFETY:` comment, following ADR 0001.
  Put VA-API / Vulkan Video FFI in `crates/platform`. If GPU interop needs `unsafe` in
  `crates/gpu`, put it in one clearly named module (e.g. `crates/gpu/src/interop.rs`), add an ADR
  (`docs/adr/0002-linux-video-interop.md`), and allow `unsafe_code` for that module only.
- **Git:** work on branch `hevc-vaapi` (or a sub-branch per phase), one commit per working step.
  `master` stays the untouched original. Ask before anything destructive or any `sudo`.
- **Every software path stays the fallback:** if hardware, Vulkan Video, VA-API or ffmpeg is
  missing or fails, FilmCraft keeps working (slower) and says why in the UI and `perf.stats`.

30. **4:2:2 handoff and 4:2:2 masters on Intel (owner, 2026-10-12).** (a) **The Intel → AMD
    GPU-to-GPU hand-off is part of 6.1b, not a fallback idea:** a 6.2K 4:2:2 10-bit frame is
    ~104 MB, so reading it back to memory and uploading it costs ~300+ MB of CPU memory traffic
    per frame (≈ 10 GB/s at 1×, ≈ 20 GB/s at 2×), which can't hold 2× and loads the CPU at 1×.
    The hand-off: the Intel media engine copies the decoded surface to a linear surface (its own
    VPP / copy engine; AMD can't read Intel tiling), exports it as a DMA-BUF
    (`vaExportSurfaceHandle`), and the AMD device imports it through the existing
    `crates/gpu/src/interop.rs` path (LINEAR modifier; biplanar P210-style layers if the driver
    offers them, else packed Y210) and copies it into VRAM once per frame with its copy engine.
    No CPU copy. Measure the read-back path first (a baseline for the before / after numbers),
    then build the hand-off; read-back stays as the fallback. Watch pitch alignment (AMD
    LINEAR needs 256-byte pitch), synchronisation (`vaSyncSurface` before the hand-off) and
    whether AMD lists LINEAR for the 16-bit formats. (b) **4:2:2 10-bit HEVC master preset on
    the Intel encoder** (`VAProfileHEVCMain422_10` EncSlice, `renderD128`): goes in **6E**, not
    Phase 6 (EXPORT-PLAN 6E.4); proxies, the render cache and YouTube stay 4:2:0.

## 3. Why the current build is slower than Resolve (the actual bottlenecks)

Raw decode speed is bounded by the VCN chip, which Resolve also uses, so that alone won't show a
big gap. Resolve's advantage is that **decoded frames never leave the GPU**: decode → grade →
scale → composite → display/encode all happen in VRAM. Today's FilmCraft path on Linux:

1. The decoder produces CPU frames (`filmcraft_frame::PixelData::Yuv16`, three planar `u16`
   planes). With the ffmpeg pipe, each 6.2K 10-bit frame (≈ 78 MB) is downloaded from VRAM, piped
   through stdout, and deinterleaved into planes on the CPU.
2. The GOP cache keeps decoded frames in RAM under `FRAME_BUDGET` = 1 GiB
   (`crates/codecs/src/gop.rs`), which is only ≈ 13 frames at 6.2K. That means constant
   re-decoding when scrubbing or playing in reverse.
3. Before upload, `crates/gpu/src/lib.rs` `prepare_frame` converts every 10-bit plane to half
   floats **on the CPU** (`codes_to_f16_bytes`), then uploads ≈ 78 MB per frame to the GPU.
4. Lumetri, keys, masks, most effects, scopes, export conversion and encoding run on the CPU.
   Only compositing, blend modes, 31 effects and 3D LUTs are on the GPU.
5. Export renders, reads back to the CPU, and encodes.

The phases below remove these one by one, then add Resolve-style caching and playback features.

## 4. How to measure (used by every phase)

Write results to `docs/fork-benchmarks.md`: one table per phase, with before/after, the exact
commands, Mesa/kernel/ffmpeg versions, and the load average. Use `cargo xtask bench` /
`bench-playback` and `perf.stats` where they apply, and extend them with new scenarios rather
than writing one-off scripts.

**Hardware ceilings (measure once in Phase 0; all targets are relative to these):**
- Decode ceiling (frames stay on the GPU):
  `ffmpeg -hwaccel vaapi -hwaccel_output_format vaapi -i CLIP -f null -` → fps.
- Decode + download ceiling: same, with `-vf hwdownload,format=p010` → fps.
- Encode ceiling: `hevc_vaapi` Main10 encode of a 3840×2160 and a 6240×4160 source already on
  the GPU → fps.
- CPU software decode: `ffmpeg -threads 0 -i CLIP_422 -f null -` → fps (4:2:2 reality check).

**Scenarios to track in every phase:**
- `xm5-play-full`: 6.2K 4:2:0 clip on a 3840×2160 29.97 timeline, Program monitor at Full, 60 s:
  frames shown/dropped, CPU ms/frame, GPU busy %, VRAM, RAM.
- `xm5-play-graded`: same clip with F-Log2 → Rec.709 conversion plus Lumetri (Basic, Curves,
  HSL secondary, vignette) and Sharpen.
- `xm5-jkl`: L at 2× and 4×, J (reverse) at 1× and 2×, K stop: dropped frames per second.
- `xm5-scrub`: 50 random seeks across a 5-minute clip: p50/p95 latency to a full-res frame.
- `xm5-multicut`: a timeline of 20 cuts alternating between 4 different clips: playback drops.
- `xm5-export-4k`: 60 s timeline → 3840×2160 HEVC Main10: export fps, ungraded and graded.
- `xm5-export-6k`: 60 s → 6240×4160 HEVC Main10 master: export fps.
- `xm5-422-play`: 4:2:2 clip, with and without proxies.

### Phase 1: Quick wins on the existing ffmpeg path

Cheap changes that cut the CPU work in half before the big rewrite:
1. Add biplanar pixel formats to `PixelData` (e.g. `P010 { y, uv }` / `Nv12`, plus a 4:2:2
   equivalent for software-decoded 4:2:2) so ffmpeg output is used as-is, with no deinterleaving.
2. Upload 10-bit planes as `R16Unorm`/`Rg16Unorm` textures and normalize in WGSL, removing the CPU
   `codes_to_f16_bytes` conversion. Keep the CPU executor as the oracle; add parity tests.
3. Read the ffmpeg pipe into pooled, reused buffers (`filmcraft_frame::pool`), with large reads.
   No per-frame allocation.
4. Make `FRAME_BUDGET` and `MAX_LIVE_DECODERS` adapt to frame size and installed RAM instead of a
   fixed 1 GiB, with a Settings ▸ Memory control.

**Accept:** `xm5-play-full` drops nothing; CPU ms/frame at least 40 % lower than Phase 0;
all parity tests pass.

### Phase 2: In-process, zero-copy hardware decode

The core change: decoded frames stay in VRAM and the compositor samples them directly.

1. **Spike both routes** (short, throwaway branches) and pick one, writing the reasoning in the
   ADR:
   - **A. Vulkan Video:** decode with `VK_KHR_video_decode_h265` on the same Vulkan device that
     wgpu uses, so decoded images are ordinary Vulkan images the compositor can sample.
   - **B. VA-API + DMA-BUF:** decode with libva, export surfaces with `vaExportSurfaceHandle`
     (DRM PRIME), import into Vulkan with `VK_EXT_external_memory_dma_buf` and
     `VK_EXT_image_drm_format_modifier`, and wrap them as wgpu textures through wgpu-hal.
   Both need control over Vulkan device creation (extra extensions and, for A, a video queue).
   Check how eframe 0.36 / egui-wgpu lets the app supply its own instance, adapter and device,
   and how wgpu 30's hal interop (`create_device_from_hal`, `create_texture_from_hal`) works.
2. Add a GPU-resident `PixelData` variant (a handle to a decoded VRAM image plus format and
   colour info), with an explicit, fallible "download to CPU" for paths that still need CPU
   pixels (CPU-only effects, the CPU oracle, scopes until Phase 4).
3. Implement the decoder behind the `VideoDecoder` trait and register it in
   `crates/platform::register()` for Linux, the way VideoToolbox is registered on macOS, so it
   gets `HybridDecoder` fallback, the Settings ▸ Playback ▸ Hardware decoding switch and the
   `decode.hardware.*` counters for free. Feed it the MOV's `hvcC` parameter sets; handle
   reordering, flush, reset/seek, disposable frames and odd sizes and crops correctly.
4. Move the GOP cache for GPU frames to a **VRAM budget** (e.g. default 6 GB of the 12 GB, set in
   Settings) with LRU eviction, so scrubbing and reverse playback reuse decoded frames like
   Resolve. Report it in `perf.stats`.
5. Keep the Phase 1 ffmpeg path as the second fallback, and the built-in software decoder last.

**Accept:** decode throughput in the app ≥ 90 % of the "frames stay on GPU" ceiling;
`xm5-play-full` drops nothing with CPU ms/frame < 3; `xm5-multicut` drops nothing; `xm5-scrub`
p95 is within 1.5× of the time to decode one GOP; a 2-hour playback soak has no VRAM/RAM growth;

### Phase 3: Resolve-style playback

1. Decode-ahead: keep N frames decoded ahead of the playhead in the play direction, sized from

4. Audio stays locked to picture during all of the above (`play_ahead.rs`), with 24-bit LPCM
   from MOV played without conversion artefacts.
5. Fix the Linux ALSA error (upstream issue #23) on PipeWire. Consider a native PipeWire output
   if cpal's ALSA host is the problem.

**Accept:** `xm5-jkl`: 1× forward and 1× reverse drop nothing; 2× and 4× show a steady,
