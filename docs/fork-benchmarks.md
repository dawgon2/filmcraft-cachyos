# Fork benchmarks: 6.2K HEVC on CachyOS + RX 6700 XT

Measurements for the fork plan (`FORK-PLAN.md` §4): one table per phase, before → after, with
the commands and versions. Wall-clock numbers depend on machine load: every run records the
1/5/15-minute load average, and runs were made with nothing else heavy running unless noted.

Scenarios run with `cargo xtask bench --sections xm5 [--only CASE] [--label NAME]`
(`crates/ui-egui/examples/bench/xm5.rs`); results land in `target/bench/bench-<label>.{json,md}`.
The bench drives the Program monitor's real frame scheduler headlessly (no window), with the
GPU compositor on the same adapter the app uses (the RX 6700 XT), and samples the GPU's
`gpu_busy_percent`, VRAM in use and the process's resident memory every 100 ms.

## Phase 0: baseline (synthetic clips)

Commit `da32409` + the bench (binary kept as `target/fork-bench/bench-phase0`), 2026-10-08,
`bench --section xm5` (full, not `--quick`): ≈ 65 min. Machine idle apart from the run (load
1–7 during decode/playback, 11–16 during the CPU-bound exports, which load it themselves).
Decode path: the system ffmpeg as a child process (`crates/platform/src/vaapi.rs`: Annex B in,
P010 out through a pipe, deinterleaved to planar `Yuv16` on 4 threads), then the CPU half-float
conversion before upload. **All synthetic.**

### Hardware ceilings (system ffmpeg, renderD129)

| ceiling | fps |
|---|---|
| decode 6.2K 4:2:0 Main10, frames stay on the GPU (`-hwaccel_output_format vaapi -f null`) | **43.2** |
| decode + download (`-vf hwdownload,format=p010`) | 34.0 |
| encode 3840×2160 Main10 `hevc_vaapi` from GPU frames (decode → `scale_vaapi` → encode) | 29.9 |
| encode 6240×4160 Main10 `hevc_vaapi` from GPU frames | 19.5 |
| CPU software decode 6.2K 4:2:2 (`-threads 0`) | 30.5 |
| CPU software decode 6.2K 4:2:0 | 34.9 |

The encode figures include the decode of the same clip in the same process, so they are a lower
bound of the encoder alone. The software-decode figures are high because x265 `ultrafast` with
noise is cheap to decode next to real camera HEVC; re-check on real clips.

Reading the playback rows: every job finishes ≈ 550 ms after it is queued (latency p50), far
behind the playhead, so the scheduler cancels it (1736 of 1736 jobs cancelled in `play-full`)
and nothing is ever shown, rather than a reduced frame rate. JKL J 2× shows 8 frames only because
reverse play does not cancel late frames. Export CPU per frame is the whole process (all threads):
the export renders and converts on the CPU (FORK-PLAN §3.4–3.5); with Lumetri it is CPU-bound at
14 s of CPU per frame and peaks at 23 GB of RAM (of 32).

### The earlier "decodes at 59 fps" figure

That was `crates/platform/examples/decode_bench.rs` on `target/fixtures/hevc4k/hevc_2160p60_10bit.mp4`
(3840×2160 60p HEVC Main10, ≈ 40 Mbit/s, 600 frames): the VA-API decoder alone (no media
stack, GOP cache or compositor), through the ffmpeg pipe including download and the CPU
deinterleave. Re-measured 2026-10-08: **59.8 fps** VA-API vs **69.8 fps** for FilmCraft's own
software decoder on this CPU. ffmpeg on the same clip: **162.5 fps** with frames on the GPU,
124.5 fps with download, so the pipe path reached 37 % of the hardware. At 6.2K (3.1× the pixels,
5× the bitrate) the same path gives 16.2 fps through the media stack, against a 43.2 fps ceiling.

## Phase 1: quick wins on the ffmpeg path (synthetic, quick pass)

Phase 1 changes (P010 biplanar frames read straight from the pipe, 16-bit normalized texture
upload, no re-zeroing of pooled planes, RAM-scaled decode cache), 2026-10-08, binary
`target/fork-bench/bench-phase1`, `--quick` (8 s plays, 10 seeks), one run each per the owner's
quick-pass rule; load 4–5. **Synthetic, quick pass.**

| scenario | Phase 0 | Phase 1 |
|---|---|---|
| decode (media stack) | 16.2 fps, 84.0 ms CPU/frame | **17.7–20.1 fps, 26.4–28.8 ms CPU/frame (−66 %)** |
| `xm5-play-full` | 0 shown, 45.8 ms CPU/frame, RSS 5.5 GB | 0 shown, **18.9 ms CPU/frame (−59 %), RSS 2.2 GB** |
| `xm5-multicut` | 0 shown, 42.1 ms, VRAM 11.3 GB, RSS 10.4 GB | 0 shown, 20.9 ms, VRAM 9.3 GB, RSS 8.8 GB |
| `xm5-scrub` | p50 1.8 s, p95 2.7 s (50 seeks) | p50 1.9 s, p95 4.3 s (10 seeks: noisy) |
| `xm5-jkl` L 2× / J 1× | 0 shown, 13.1 / 13.6 ms | 0 shown, 7.1 / 6.9 ms |

The ffmpeg pipe ceiling (§1a.5 of the plan): ffmpeg itself delivers 6.2K P010 at 30.5 fps to
`-f null` but only 22.2 fps through a pipe (unchanged with a 1 MiB pipe buffer: ffmpeg's
download and write are serial). FilmCraft's decoder now reaches 18–20 fps, 80–90 % of that, so
playback still cannot reach 29.97 fps on this path and shows nothing (the scheduler issue, Phase
3). The CPU and memory wins carry over; real-time 6.2K is Phase 2's job (no pipe, no download).

**Soak:** 120 min, 214 314 shown / 3 dropped, RSS 187–227 MB without a trend, VRAM flat after
warm-up (FORK-PLAN §7). **Fallback:** in-process → ffmpeg pipe → software tested; VA-API
pulled → software (13.7 fps); Vulkan import off → read-back path (240/0, quick).
